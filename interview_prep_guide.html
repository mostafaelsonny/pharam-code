القاعدة الذهبية للمقابلة

الإنترفيو مش امتحان syntax. هو مقياس: هل تقدر تبرر قراراً هندسياً، تعترف بحدوده، وتقترح تحسيناً من غير ما تدافع عن الكود لأنك كتبته؟ لو المحاور قال إن فيه طريقة أحسن: لا ترفض أوتوماتيك، ولا توافق من غير فهم. ناقش الـ trade-off.

لو قالك «الطريقة دي مش الأفضل» هترد إزاي؟

الصيغة اللي بتثبت engineering mindset:

«أتفق من منظور الإنتاج، لأن X. أنا اخترت الطريقة الحالية لأني كنت بأُحسّن لـ Y (سرعة الـ MVP / بساطة الديمو). القيد الموجود فعلاً هو Z. لو بأحسّن المشروع دلوقتي هحوّلها لـ X.»

ده مش ضعف. ده معناه إنك مش مرتبط عاطفياً بالكود، وإنك فاهم إن كل قرار له تكلفة.

خريطة المشروع في دقيقة

MediScout بيعمل إيه؟ ومين الأطراف؟

MediScout منصة صيدلية ذكية: المريض يرفع صورة روشتة → Gemini يستخرج الأدوية → النظام يطابق المخزن ويقترح بدائل → الصيدلي يراجع → المريض يقبل/يرفض البدائل ويدفع (كاش أو Stripe) → المندوب يحدّث حالة التوصيل. كل خطوة ليها إشعار لحظي بـ Socket.IO.

الدوربيعمل إيه
user (مريض)رفع روشتة، قرارات البدائل، checkout، تتبع الطلب
pharmacistمراجعة الروشتات المسندة له، تعديل الأصناف، المخزن
deliveryاستلام الطلبات المسندة، PROCESSING / COMPLETED / CANCELLED
adminإدارة المستخدمين، الأدوار، الحظر، إنشاء صيدلي/مندوب
صورة روشتة → Gemini Vision → مطابقة Drug + Interaction → PENDING_PHARMACIST_REVIEW → اعتماد الصيدلي → READY_FOR_CART → قرارات المريض + Checkout → ORDER_PENDING → ORDER_PROCESSING → ORDER_COMPLETED

الاستاك الفعلي: React 19 + TypeScript + Vite + Redux Toolkit + TanStack Query + Zod على الفرونت. Express 5 + MongoDB/Mongoose + JWT + Socket.IO + Gemini + Stripe على الباك. النشر: Vercel (فرونت) + Railway (باك) + MongoDB Atlas.

1. المعمارية — Architecture

ليه قسمت الـ Backend إلى routes / controllers / models / middleware؟ ليه مش الـ logic كله في الـ routes؟

عشان Separation of Concerns وSingle Responsibility:

  • Routes: توصيل الـ HTTP method والمسار بالـ handler، وترتيب الـ middleware (protect ثم authorize).
  • Controllers: الـ business logic الحالي: Gemini، المطابقة، الـ transaction، Stripe.
  • Models: شكل البيانات، الـ enums، hooks زي تشفير الباسورد في userModel.
  • Middleware: اهتمامات عرضية: مين المستخدم؟ هل الدور مسموح؟ من غير تكرار في كل endpoint.

لو اللوجيك في الـ routes: الملفات تتضخم (fat routes)، الاختبار يبقى مربوط بـ req/res، ومش هقدر أعيد استخدام نفس قاعدة «خصم المخزن» من مسار تاني (checkout والكاش وverify Stripe).

أمانة عن الكود الحالي: مفيش مجلد services منفصل. الـ controllers مسؤولة عن اللوجيك كله. الـ README بيتكلم عن services كاتجاه معماري، لكن التنفيذ الحالي Controller-centric. لو المشروع كبر هطلع Gemini matching و Stripe و stock deduction لطبقة services عشان الـ controller يفضل رفيع.
إيه معنى Clean Architecture في مشروعك تحديداً؟

مش معناه إن عندي hexagonal كامل. معناه إن حاولت أفصل:

  • قواعد العمل (حالات الروشتة، مين يقدر يعمل transition، السعر يتحسب من السيرفر مش من الفرونت).
  • آلية التوصيل (Express routes، Socket emitters، Stripe session).
  • شكل التخزين (Mongoose schemas).

مثال حي: إجمالي الفاتورة في الـ checkout بيتحسب تاني من الـ items في الداتابيز، مش بنصدّق الرقم اللي جاي من الفرونت. دي قاعدة عمل مستقلة عن الـ UI.

على الفرونت: تنظيم feature-based (auth / prescriptions / pharmacist / inventory / delivery / admin) بدل مجلدات components مسطحة، عشان كل دومين يملك الـ UI والـ hooks والـ API بتوعه.

ليه Express monolith مش NestJS أو microservices؟

حجم المشروع وفريق من شخص واحد. Express واضح، سريع للـ MVP، وSocket.IO بيتوصل بسهولة على نفس الـ HTTP server. Nest كان هيضيف boilerplate قبل ما تثبت الـ workflow. Microservices دلوقتي هتكون overengineering: شبكة، tracing، عقود بين خدمات، من غير مستخدمين كفاية تبرر التكلفة.

لو كبر 10×: هفضل monolith منظم أطول فترة ممكنة، وأطلع أول حاجة تقيلة برّه: معالجة Gemini على worker + queue، لأن دي العملية اللي بتحجز الـ event loop.
ليه في server.js عملت http.createServer(app) بدل app.listen؟

Socket.IO محتاج نفس الـ HTTP server عشان يعمل upgrade من HTTP لـ WebSocket. لو سمعت Express لوحده، الـ REST هيشتغل والسوكت لأ. علشان كده: connectDB → Express app → http.Server → initSocket(server) → server.listen(PORT, '0.0.0.0').

0.0.0.0 مهم في Railway/Docker: السيرفر يسمع على كل الواجهات مش localhost بس، وإلا الـ reverse proxy مش هيوصل.

إيه اللي كنت هتغيره لو المشروع كبر 10×؟
  • طبقة services حقيقية + error middleware مركزي.
  • Gemini على job queue (BullMQ + Redis): الرد الفوري «جاري التحليل» بدل انتظار الـ AI داخل نفس الـ request.
  • الصور على object storage (S3) مش Base64 جوه Mongo.
  • Socket.IO Redis adapter لو أكتر من instance.
  • فهارس + pagination إلزامي على الروشتات.
  • Webhook Stripe بدل الاعتماد على صفحة النجاح.
  • مصادقة السوكت بالـ JWT.

المعيار: مش «أضيف Redis لأن الشركات بتستخدمه»، المعيار: المشكلة ظهرت عند حجم معيّن، ساعتها الأداة دي بتحل Y.

ليه الفرونت TypeScript والباك JavaScript؟

الـ UI فيه كيانات متداخلة (Prescription, Item, Role, statuses) والـ contract مع الـ API بيتكرر في صفحات كتير؛ TypeScript بيقلل أخطاء الـ props والـ slices. الباك بدأ أسرع بـ JS modules عشان الـ iteration على Gemini والـ workflow. لو كملت المشروع: هحوّل الباك لـ TypeScript أو على الأقل أشارك types عبر OpenAPI.

لو سألوك «ده مش consistent»: «صح، ده دين تقني واعي. أولوية الـ typing كانت أعلى في الفرونت لأن تكلفة الـ runtime error هناك أوضح للمستخدم.»

2. Authentication & Authorization

الفرق بين Authentication و Authorization في مشروعك؟

Authentication: إثبات الهوية. الـ JWT بعد login/register، وprotect بيتحقق إن التوكن صحيحة والمستخدم موجود ومش محظور.

Authorization: إثبات الصلاحية. authorize('pharmacist') على طابور الصيدلي، ومقارنة prescription.pharmacistId === req.user._id قبل الاعتماد. الأدمن يقدر يفتح صفحة المستخدمين؛ الصيدلي لأ. الصيدلي يقدر يعتمد روشتته هو، مش روشتة صيدلي تاني.

على الفرونت: ProtectedRoute بيمنع عرض الصفحة. ده UX مش أمان. الأمان الحقيقي على الباك.

ليه JWT أصلًا؟ ليه مش Sessions؟

الفرونت على Vercel والباك على Railway: دومينين مختلفين. الـ JWT stateless: أي instance من الباك يقدر يتحقق بالتوقيع من غير sticky session ومن غير تخزين الجلسة في مونجو. مناسب لـ REST + SPA.

الـ Sessions الكلاسيكية (cookie + store) أحسن لو نفس الدومين وعايز revoke فوري وcsrf مضبوط. تكلفتها: session store (Redis)، CORS cookies (credentials، SameSite)، وتعقيد مع Socket.IO.

اختياري للـ MVP: JWT في الهيدر Authorization: Bearer.

التوكن عندي صالحة 30 يوم، ومفيش refresh token ومفيش blacklist. لو اتسرّبت تفضل شغالة لحد ما تنتهي، إلا لو حظرت المستخدم (isBlocked بيتشيك في كل request بعد الـ verify).
التوكن بتتحط فين؟ مين بيعمل verify؟ السيرفر يعرف المستخدم إزاي؟
  1. بعد login/register الباك بيرجع token + بيانات المستخدم.
  2. الفرونت يخزن auth_token وauth_user في localStorage (جوه authSlice).
  3. apiClient interceptor بيحط Bearer على كل طلب.
  4. protect يعمل jwt.verify(token, JWT_SECRET)، ياخد decoded.id، يجيب المستخدم من مونجو select('-password')، ويحطه على req.user.

الباك عمره ما يثق في userId اللي في الـ body لو المسار محمي. مثال: getMyPrescriptions بفلتر userId: req.user._id من التوكن مش من الفرونت.

إيه مشاكل تخزين التوكن في localStorage؟ هل JWT لوحده كفاية؟

أي XSS يقدر يقرأ localStorage ويسرق الجلسة. الـ httpOnly cookie أصعب على السكربتات، لكنها تحتاج إعداد CSRF وCORS cookies.

JWT لوحده مش كفاية: محتاج HTTPS، صلاحية معقولة، تحقق من الحظر، وauthorization على مستوى المورد (ownership)، ومعدل طلبات، ومراجعة دور التسجيل (محدش يسجّل نفسه صيدلي).

عندي: التسجيل دايمًا role: 'user'. الصيدلي والمندوب والأدمن بيتخلقوا من الأدمن. ده قرار أمني صح.

إزاي منعت صيدلي يعدّل روشتة مش بتاعته؟

طبقتين:

  1. protect + authorize('pharmacist') على PUT /:id/pharmacist-approve — لو مش صيدلي → 403.
  2. داخل approveByPharmacist: لو prescription.pharmacistId !== req.user._id → 403 «غير مصرح لك بتعديل هذه الروشتة».

نفس الفكرة للمندوب في updateDeliveryStatus مع deliveryId.

الجلب كمان مفلتر: طابور الصيدلي pharmacistId: req.user._id + status المراجعة. مش بنرجّع روشتات العالم كله.

إيه فايدة optionalProtect؟ ليه الزائر يقدر يرفع روشتة؟

تجربة المريض: يصور الروشتة من غير حساب، ويشوف النتيجة. لو فيه توكن، بنربط userId. لو مفيش، الروشتة تتخلق من غير مستخدم وتتربط عند الـ checkout (prescription.userId = req.user._id) لأن الـ checkout نفسه ورا protect.

ده trade-off بين التحويل (conversion) وبين التتبع. القيد: روشتات يتيمة ممكن تتراكم، ومسار جلب الروشتة بالـ ID مفتوح نسبيًا.

إيه حكاية isInitialized في الفرونت؟

عند أول تحميل: فيه توكن في localStorage، وgetProfileThunk لسه ما خلصش. لو ProtectedRoute حكم من isAuthenticated === false هيرمي المستخدم للوجين وهو أصلًا لوجد إن. isInitialized معناها: «خلّصت محاولة التحقق». طول ما هي false نعرض لودينج. بعدين نقرر login أو دخول.

دي قصة engineering حلوة: race بين الـ persist والـ async verification.

الحظر isBlocked بيشتغل إزاي؟

الأدمن يعمل toggle. في اللوجين: لو محظور → 403. في كل طلب محمي: بعد verify، لو req.user.isBlocked → 403. يعني حتى لو التوكن لسه صالحة، الجلسة تموت على أول API call. مفيش حاجة تلغي التوكن نفسها على السوكت إلا لو قفلنا الاتصال يدويًا.

3. Redux Toolkit و TanStack Query

ليه Redux أصلًا؟ ليه مش Context API لكل حاجة؟

عندي حالة بتتكتب من أماكن كتير ومش شجرة مكوّنات واحدة: رفع روشتة، داشبورد صيدلي، صفحة نجاح Stripe، AuthInitializer، سوكت. Redux Toolkit اداني store واحد، slices واضحة، وcreateAsyncThunk لحالات loading/error.

Context ينفع لحالة نادرة التغيير (ثيم، لغة). لو حطيت الروشتات والأوث في Context من غير تقسيم، أي تحديث للـ currentPrescription يعيد رسم شجرة كبيرة. كمان منطق الـ extraReducers للـ async أدق من useEffect متناثر.

ليه مش PharmacistDashboard يمسك الـ state ويبعتها props؟

لأن الإشعار لازم يوصل حتى لو الداشبورد مش متركب. حطيت listeners في AuthInitializer على مستوى التطبيق. لو الحالة عايشة جوه الداشبورد بس: المستخدم لو راح للملف الشخصي هيفوت إشعار، أو هتحتاج prop drilling عبر Layout. الـ store هنا bus للأحداث عبر الصفحات.

وفي نفس الوقت: حالة المودال المفتوح (selectedPrescription, isReviewOpen) محلية في usePharmacistDashboard لأنها UI state مش محتاجة تبقى global.

إيه الفرق بين server state و client state؟ إيه اللي يستحق يبقى global؟

Server state: نسخة من الداتابيز ممكن تتقادم (قائمة أدوية، قائمة يوزرز). الأفضل cache + invalidate. ده عندي بـ TanStack Query في المخزن وإدارة المستخدمين: queryKey: ['drugs', params] وبعد الـ mutation invalidateQueries.

Client state: اختيار الصيدلي قبل الرفع، قرار قبول بديل لحظي قبل الحفظ، حالة المودال، التوكن بعد اللوجين.

Global عندي في Redux: auth (مستخدم عبر كل الـ ProtectedRoute)، currentPrescription ومسارها عبر صفحات متعددة + سوكت، طوابير الصيدلي/المندوب لأنها بتتحدث من خارج الشاشة.

ليه الاتنين مع بعض؟ الروشتة مش CRUD عادي: تدفق + أحداث لحظية + قرارات محلية قبل الـ persist. المخزن CRUD كلاسيكي Query بتلمع فيه. لو حطيت الأدوية في Redux كنت هأعيد اختراع cache.
إمتى Redux يبقى overkill؟

صفحة واحدة، مفيش سوكت، مفيش مشاركة حالة عبر راوتس. ساعتها useState + React Query كفاية. MediScout فيه 4 أدوار وworkflow أطول من شاشة؛ Toolkit هنا مش استعراض، هو تقليل مصدر الحقيقة المتناقض.

إيه فايدة toggleAlternativeDecision في الـ slice؟

ده client state: المريض يضغط قبول/رفض بديل، الإجمالي يتحدث فورًا من غير راوند تريب. بعدين بن싱크 السيرفر بـ updatePatientDecisions أو مع الـ checkout. السعر النهائي برضو بيتحسب من السيرفر عشان محدش يزوّر الإجمالي.

4. Socket.IO والوقت الفعلي

ليه Socket.IO؟ ليه مش polling؟ ليه مش SSE؟

Polling: كل كام ثانية GET. بسيط، لكن تأخير + ضغط على السيرفر والداتابيز، خصوصًا لو 100 صيدلي فاتحين الداشبورد.

SSE: سيرفر → عميل فقط، فوق HTTP. ممتاز للإشعارات في اتجاه واحد. عندي أحداث من المريض للصيدلي والعكس والمندوب؛ وفي المستقبل ممكن أحتاج قنوات أوسع. كمان SSE وراء بعض البروكسيات أصعب، ومفيش rooms جاهزة.

Socket.IO: ثنائي الاتجاه، rooms، fallback لـ polling لو الـ WebSocket اتقفل (الـ client عندي transports: ['websocket', 'polling'])، وreconnect.

Socket.IO بيشتغل فوق Engine.IO، والـ WebSocket نفسه upgrade لبروتوكول ثنائي الاتجاه على اتصال TCP طويل، عكس HTTP request/response اللي بيقفل بعد الرد.

ليه rooms؟ ليه user_${userId} وrole_pharmacist؟

الـ room قناة بث لمجموعة سوكتات. user_abc توصل لنفس الشخص على أكتر من تاب. pharmacist_${id} للصيدلي المحدد. role_pharmacist لو حبيت أنبه كل الصيادلة (عندي مستخدم كـ fallback).

النية الهندسية: توجيه الحدث للطرف الصح بدل ما كل العملاء يفلتروا.

التنفيذ الحالي للديمو: بعد ما بعت للـ rooms، في notifyPharmacistNewPrescription وnotifyPatientPrescriptionStatus فيه io.emit(...) بث عام لكل المتصلين. كمان join_room بياخد userId وrole من العميل من غير JWT على السوكت. أي عميل يقدر يدّعي إنه صيدلي وينضم للرومات. CORS السوكت origin: '*'.
الجملة الجاهزة: «التنفيذ مناسب لـ MVP/إنترفيو ديمو. في production هوثّق السوكت بالـ JWT عند الـ handshake، الهوية من التوكن مش من العميل، وهشيل الـ broadcast العام، وهحدد origin.»
مين المفروض يحدد هوية المستخدم؟ هل نصدّق العميل لو قال أنا pharmacist؟

المفروض السيرفر فقط، بعد verify للتوكن. حالياً العميل في socketService.joinUserRoom(user._id, user.role) بعد ما Redux يعرف المستخدم من الـ profile — يعني النية صح على الفرونت، لكن الباك مش بيفرضها. ده أضعف نقطة real-time عندي وأنا واعي بيها.

ليه listeners في AuthInitializer مش بس في الداشبورد؟ وليه BroadcastChannel؟

في الإنتاج اكتشفنا إن الـ listener لو اتربط بمكوّن بيتفك عند التنقل، فالصيدلي ممكن يكون على صفحة تانية ومفيش تحديث. الحل: اشتراك دائم حسب الدور في AuthInitializer.

BroadcastChannel('prescription_events') تزامن بين تبويبات نفس المتصفح (رفع روشتة في تاب وداشبورد في تاب تانية) حتى لو السوكت اتأخر. ده مكمل محلي، مش بديل للسيرفر.

5. MongoDB ونمذجة البيانات

ليه MongoDB مش PostgreSQL؟ إمتى الـ relational أنسب؟

الروشتة document غني ومتداخل: patientInfo، items بأحوال توفر وبدائل وقرارات، تحذيرات تفاعل، صورة. قراءتها كوحدة واحدة طبيعية في document store، والتطوير أسرع مع Mongoose.

PostgreSQL أنسب لو: تقارير مالية معقدة، قيود علاقات صارمة عبر جداول كتير، joins تقيلة، متطلبات ACID على مستوى النظام كله من اليوم الأول، أو فريق أصلاً SQL.

المخزن والكميات علاقات أوضح في SQL، وأنا عوّضت بـ transaction + findOneAndUpdate الشرطي.

إمتى embedding وإمتى referencing؟ ليه pharmacistId وuserId reference؟

Embedded items: لقطة (snapshot) لحالة الصنف وقت الروشتة: الاسم، السعر، الجرعة، قرار المريض. لو سعر الدواء اتغيّر بعد أسبوع، الفاتورة القديمة متتغيرش. كمان الروشتة تتقرا كاملة من غير populate لكل سطر.

drugId reference: عشان نخصم من نفس سجل المخزن.

userId / pharmacistId / deliveryId: مستخدمين بيتحدثوا (اسم، حظر، دور). مرجع مش نسخ، مع populate للاسم والإيميل عند العرض.

warningsFound embedded: نتيجة الفحص وقت التحليل، أرشيف طبي للروشتة دي.

originalImage embedded Base64: سهل للديمو، سيئ للإنتاج (حجم المستند، الـ 16MB limit، الـ backups).

إيه الـ transaction في الـ checkout؟ إيه مشكلة الـ consistency اللي بتحلها؟

الـ checkout بيعمل أكتر من كتابة: تحديث الروشتة + خصم أكتر من دواء. من غير transaction: ممكن أخصم دواءين والتالت يفشل، أو أخصم المخزن والـ save يفشل فالأوردر ما يتسجلش.

استخدم mongoose.startSession() وwithTransaction. الخصم: findOneAndUpdate({ stockQuantity: { $gte: qty } }, { $inc: { stockQuantity: -qty } }) داخل نفس الـ session. لو الكمية مش مكفية → 409 والعملية كلها ترجع.

دي حماية من lost update / oversell: مريضين يطلبوا آخر علبة في نفس اللحظة.

نفس النمط في verifyStripePayment بعد التأكد إن Stripe paid.

Transactions في Mongo محتاجة replica set. Atlas بتوفّرها. لو حد سألك على local Mongo قديم: هتفشل.
ليه السعر والكمية مش بنصدق الفرونت؟

أي عميل يقدر يعدل JSON. الإجمالي يتحسب على السيرفر من items المخزّنة وقرارات القبول. Stripe line_items كمان من السيرفر بالجنيه × 100 (قروش) لأن Stripe بيشتغل بأصغر وحدة عملة.

فيه indexes؟ الـ email unique؟

email unique في user schema. غير كده الـ queries زي Prescription.find({ pharmacistId, status }) وDrug.find({ tradeName: regex }) من غير index صريح. مع آلاف الروشتات هيمشي؛ مع مئات الآلاف هيبقى collection scan. الإنتاج: index مركّب { pharmacistId: 1, status: 1, createdAt: -1 } ونفس الفكرة لـ userId و deliveryId.

موديل Interaction والتداخل الدوائي؟

أزواج مواد فعالة + خطورة CRITICAL/MODERATE/LOW. بعد استخراج أدوية الروشتة، بنجمع المواد ونبحث ingredientA $in list AND ingredientB $in list. النتيجة بتتخزن في warningsFound عشان الصيدلي يشوفها. في الـ seeder مثال warfarin + diclofenac.

القيد: مش محرك دوائي كامل (جرعات، أمراض مزمنة). قاعدة بيانات صغيرة للديمو الطبي.

6. دورة حياة الروشتة — أهم جزء

احفظ الـ state machine، مش الكود
PENDING → PENDING_PHARMACIST_REVIEW → READY_FOR_CART → ORDER_PENDING → ORDER_PROCESSING → ORDER_COMPLETED READY_FOR_CART ──→ CANCELLED (عن طريق المندوب حالياً من الحالات المسموحة بعد الإسناد) ORDER_PENDING ──→ ORDER_PROCESSING | ORDER_COMPLETED | CANCELLED
الحالةالمعنىمين يحرّك
PENDINGمذكورة في الـ enum كاستخراج AIعملياً الـ create بيحط مراجعة الصيدلي مباشرة
PENDING_PHARMACIST_REVIEWالصيدلي لازم يراجعprocessPrescription
READY_FOR_CARTمعتمدة وفي انتظار شراء المريضapproveByPharmacist
ORDER_PENDINGطلب اتأكد (كاش أو دفع كارد ناجح)checkout أو verifyStripe
ORDER_PROCESSINGالمندوب بدأ التوصيلupdateDeliveryStatus
ORDER_COMPLETEDتم التسليمالمندوب
CANCELLEDإلغاء مع سبب اختياريالمندوب (الحالات المسموحة في الكود)
ليه statuses مش Boolean زي isApproved؟

الـ Boolean يوصف بعد ثنائي واحد. هنا مسار متعدد: مراجعة ≠ جاهزة للسلة ≠ قيد التجهيز ≠ في الطريق ≠ مكتملة ≠ ملغاة. لو عملت isApproved و isPaid و isDelivered هتلاقي تركيبات مستحيلة (delivered من غير paid). الـ enum آلة حالات: في لحظة واحدة حالة واحدة.

كمان الفلترة بسيطة: طابور الصيدلي = status واحدة. سجل المريض = مجموعة حالات.

الفرق بين اعتماد الصيدلي وتجهيز الأوردر؟

Pharmacist approval: قرار طبي/صيدلي على الأصناف والبدائل والملاحظات. بيحوّل READY_FOR_CART ويحسب الإجمالي من الأصناف المتوفرة. المريض لسه ما اشترى.

Order processing: لوجستيات بعد ما الطلب اتأكد: خصم مخزن حصل، مندوب، توصيل. مينفعش المندوب «يعتمد بديل دوائي». مينفعش الصيدلي من المسار الحالي يعلّم ORDER_COMPLETED.

إيه اللي يمنع transition غلط؟

أمثلة من الكود:

  • Checkout لو status مش READY_FOR_CART → 400 «غير جاهزة أو تم طلبها».
  • المندوب يقبل بس PROCESSING / COMPLETED / CANCELLED.
  • Stripe session لو مش READY_FOR_CART → 400.
  • الصيدلي لازم ownership.
مفيش آلة حالات مركزية (state machine table). القواعد موزعة جوه الـ controllers. ينفع في الحجم الحالي؛ لو كبر هعمل دالة assertTransition(from, to, actor) عشان منساش مسار.
مسار الصنف جوه الروشتة (مش حالة الروشتة)

كل item له:

  • availabilityStatus: AVAILABLE / ALTERNATIVE_AVAILABLE / OUT_OF_STOCK
  • reviewStatus: PENDING_REVIEW → APPROVED (بعد الصيدلي)
  • patientDecision: ACCEPTED / REJECTED للبديل

سجل المريض يخفي READY_FOR_CART لو مفيش صنف قابل للشراء (كله نفذ أو المريض رفض البدائل). ده فلتر منتج مش status جديدة.

ملاحظة مهمة: READY_FOR_CART بعد الـ AI مباشرة نادرة

في processPrescription كل فروع المطابقة بتحط requiresPharmacistReview = true. يعني عملياً كل روشتة بتدخل مراجعة صيدلي. المتغير والفرع READY_FOR_CART موجودين كتصميم مستقبلي (روشتة واضحة 100% ومخزن كامل من غير لبس) لكن دلوقتي المسار الإلزامي هو المراجعة البشرية — وده منطقي طبياً.

7. Gemini واستخراج الروشتة

ليه التحليل على الباك مش الفرونت؟

مفتاح Gemini سري. لو اتحط في الفرونت أي حد يسرقه. كمان منطق المطابقة مع المخزن لازم يشوف الداتابيز. الفرونت بيبعت الصورة Base64 + بيانات التواصل + pharmacistId.

خطوات processPrescription بالترتيب
  1. تحقق من الصورة والتليفون والعنوان وpharmacistId.
  2. Gemini Vision يرجع JSON أدوية (اسم تجاري، مادة فعالة، جرعة).
  3. لكل دواء: مطابقة tradeName في المخزن وكمية > 0، وإلا بديل بنفس المادة الفعالة، وإلا OUT_OF_STOCK.
  4. جمع المواد وفحص Interaction.
  5. إنشاء Prescription بحالة المراجعة، وتخزين الصورة.
  6. notifyPharmacistNewPrescription.
المطابقة بـ regex case-insensitive ممكن تمسك اسم جزئي غلط. JSON.parse على رد Gemini من غير تنظيف markdown ممكن يكسر لو الموديل لف الرد في ```. الـ body limit 50mb عشان الصور؛ ده باب كبير لو مفيش rate limit.
ليه الكمية الافتراضية 1؟

الـ OCR مش دايمًا بيقرا الكمية بثقة. الصيدلي يقدر يعدّل الأصناف قبل الاعتماد. قرار MVP: دقة أقل في الكمية مقابل عدم اختراع رقم. في الإنتاج: prompt أقوى + تأكيد صيدلي إلزامي على الكمية.

8. Stripe والمدفوعات

ارسم تدفق الدفع
User (READY_FOR_CART) → POST create-checkout-session (protect) → Stripe Checkout hosted page → Payment → success_url?session_id=... → CheckoutSuccessPage ينادي verify-payment → السيرفر retrieve session من Stripe → لو paid: transaction خصم مخزن + ORDER_PENDING

مسار الكاش: checkout مباشر على السيرفر من غير Stripe، نفس خصم المخزن والتحول ORDER_PENDING.

ليه الـ secret على الباك والـ publishable على الفرونت؟

Secret key يقدر يعمل تحويلات ويقرأ عملاء. أي كشف = كارثة مالية. Publishable key مصممة للمتصفح لبدء عناصر الدفع، ومش بتعمل capture لوحدها.

حالياً بنحوّل المستخدم لـ session.urlhosted؛ الـ publishable أقل مركزية مما لو Stripe.js عناصر مدمجة. المبدأ ثابت: أسرار السيرفر متطلعش.

هل الفرونت يقدر يقول «أنا دفعت» ونصدقه؟ ليه صفحة النجاح مش كفاية؟ ليه Webhook؟

لأ. أي حد يفتح /checkout/success/:id. علشان كده verify بيسأل Stripe عن الـ session، يطابق client_reference_id مع الروشتة، ويطابق metadata.userId مع req.user، ويتأكد payment_status === 'paid'.

مشكلة صفحة النجاح وحدها: المستخدم يقفل التاب قبل ما الـ request يتم، الشبكة تقطع، فيتحول فلوس وتتخصمش من المخزن أو العكس.

Webhook checkout.session.completed رسالة من Stripe لسيرفرك مع توقيع. ده مصدر الحقيقة في الإنتاج، ويشتغل حتى لو المستخدم اختفى.

«التحقق من صفحة النجاح موجود كـ MVP. مخطط الإنتاج: webhook + نفس منطق الـ idempotency. صفحة النجاح تبقى UX مش مصدر تأكيد الدفع.»
إيه idempotency هنا؟

نفس عملية التأكيد لو اتنفذت مرتين متخصمش المخزن مرتين. في verify: لو الحالة أصلًا ORDER_PENDING/PROCESSING/COMPLETED نرجع نجاح من غير خصم. وجوه الـ transaction نفس الفحص تاني (سباق بين تبويبين). ده يدوي. Stripe كمان بيدعم Idempotency-Key على إنشاء الـ session.

ليه FRONTEND_URL في بيئة السيرفر؟

Stripe يحتاج success/cancel مطلقين. في المحلي localhost:5173، في الإنتاج دومين Vercel. لو سيبناها localhost والمستخدم على Vercel، بعد الدفع هيرجع لعنوان مش موجود.

9. الأخطاء والتحقق

ليه centralized error handling؟ عندك موجود؟

الفكرة: controllers ترمي Error بعد ما تحدد res.status، وmiddleware أخير يوحّد شكل JSON ويتجنب سقوط البروسيس.

أنا استخدم express-async-handler عشان الـ reject يروح لـ next(err). لكن مفيش error middleware مسجّل في server.js ولا notFound. في Express 5 السلوك أحسن من 4، لكن الاستجابة مش موحّدة بالشكل الاحترافي.

«ده دين تقني. الخطوة الجاية: errorHandler يرجّع {message} ويتكلم، ويميّز CastError و ValidationError عن 500 العام.»
الفرق بين 400 401 403 404 409 500
الكودالمعنى في MediScout
400طلب غلط: نقص صورة، checkout والحالة مش جاهزة، session مش للروشتة
401مش متعرّف: مفيش توكن / توكن بايظة / يوزر اتمسح
403متعرّف لكن ممنوع: دور غلط، صيدلي تاني، محظور، session مش لمستخدمك
404المورد مش موجود
409تعارض: المخزن اتنقص قبل ما تخلّص
500فشل سيرفر: Stripe مش متهيأ، انهيار غير متوقع
طبقات التحقق: Validation vs Authn vs Authz vs Business vs DB
  • Validation: Zod على الفرونت (تليفون مصري، عنوان). على الباك فحوصات يدوية (حقول مطلوبة). الفرونت للراحة؛ الباك للحماية.
  • Authentication: توكن.
  • Authorization: دور + ملكية المورد.
  • Business rules: READY_FOR_CART قبل الدفع، كمية مخزن، أصناف مقبولة فقط.
  • DB errors: duplicate email، سقوط أطلس.

لو مونجو وقعت: الاتصال في connectDB يعمل process.exit(1) عند البدء. أثناء التشغيل الطلبات هتفشل. في الإنتاج: healthcheck GET /health + إعادة تشغيل Railway + مراقبة.

هل أثق في الـ input من الفرونت؟ لا. أبداً.

مسارات الأدوية من غير protect — هتعترف بيها؟

نعم. drugRoutes مفيهاش protect/authorize. أي حد يعرف الـ API يقدر يضيف أو يمسح دواء. الواجهة بتظهر المخزن للصيدلي/أدمن فقط، بس ده مش أمان. نفس الفكرة تقريبًا لـ interactions/check.

«دي ثغرة واضحة في الـ MVP. هقفّلها authorize('pharmacist','admin') على الكتابة.»

10. الفرونت: راوتنج، أداء، نماذج

ليه lazy loading للصفحات؟

المريض مش محتاج باقة الأدمن. React.lazy + Suspense في routes/index.tsx يقلل الـ bundle الأولي. App نفسها رفيعة: Router فقط، والـ AuthInitializer برّه في main.

ProtectedRoute على الفرونت يكفي؟

لأ. ده لمنع الضياع في الـ UX. المهاجم يعدّي الراوتر وينادي الـ API. الدفاع: middleware الباك.

ليه React Hook Form + Zod؟

التحكم في فورم كبير (رفع روشتة / checkout) من غير إعادة رسم كل حرف. Zod schema مصدر حقيقة لنوع البيانات ورسائل عربي. بس ده الطبقة الأولى فقط.

ليه Axios interceptor؟

مكان واحد لإضافة التوكن وbaseURL من VITE_API_URL. من غير كده كل service هتنسى الهيدر.

Pagination على الأدمن والمخزن

getUsers و getDrugs: page/limit/skip + countDocuments. الواجهة مش بتجيب كل اليوزرز. الروشتات عند الصيدلي لسه find() من غير صفحات — مقبول لطابور صغير، مش لمليون مستند.

11. الأدوار، الأدمن، المخزن، التوصيل

مين بيخلق الصيدلي والمندوب؟

التسجيل العام user فقط. الأدمن POST /api/users يختار role. قوائم الصيادلة/المناديب للمريض: مستخدمين role مناسب وisBlocked: false، ومش بنرجّع باسورد.

الأدمن مينفعش يحظر أو يحذف نفسه.

كلمة السر

bcrypt في pre('save') لو الباسورد اتعدّل. المقارنة matchPassword. عمرنا ما نرجّع حقل password في الـ JSON (select('-password')).

المخزن ليه Query مش Redux؟

CRUD + فلاتر + cache. بعد create/update/delete نعمل invalidate لمفتاح drugs. مفيش سوكت على تغيير السعر حالياً. لو حبيت كل الكاشيرات تشوف الكمية لحظياً بعد checkout، ساعتها إما invalidate من حدث سوكت أو تحدث الـ query.

12. النشر، CORS، البيئة

ليه Vercel للفرونت وRailway للباك وAtlas للداتابيز؟

Vercel: CDN، بناء Vite تلقائي، مناسب لـ SPA ثابتة. مش مناسب لسوكت طويل العمر (serverless functions بتروح للنوم).

Railway: بروسيس Node مستمر، WebSocket، PORT من البيئة، مناسب لـ Express + Socket.IO. (بعض الوثائق القديمة ممكن تذكر Render؛ المبدأ واحد: سيرفر طويل العمر مش serverless).

Atlas: replica set جاهز للـ transactions، نسخ احتياطي، من غير ما أدير VM.

يعني إيه Origin؟ ليه CORS ظهر بعد ما local كان شغال؟

المتصفح بيمنع فرونت على دومين (mediscout.vercel.app) ينادي API على دومين تاني (railway) إلا لو السيرفر يبعت رؤوس CORS تسمح بالـ Origin ده. على localhost أحيانًا الأدوات أهدى أو نفس الجهاز فتخيّل إن مفيش مشكلة، أو cors() مفتوح للكل فعدّى.

عندي app.use(cors()) يسمح لأي origin — سهل للديمو وخطر في الإنتاج لو الـ API عليه عمليات حساسة من غير قيود تانية. المفروض whitelist لـ FRONTEND_URL.

ليه environment variables؟ ليه PORT من البيئة؟

الأسرار والمنافذ بتختلف بين جهازك وRailway. المنصة تعيّن PORT؛ لو سمعت 5000 ثابت في الإنتاج البروكسي مش هيلاقيك. الفرونت: أي متغير لازم يبدأ بـ VITE_ عشان يتحقن وقت البناء — وده يعني مفيش أسرار حقيقية في فرونت Vite.

ليه local اشتغل وproduction ظهر case-sensitivity؟

ويندوز غالباً case-insensitive. Linux (Vercel/Railway) حساس. استيراد ./Index.css لازم يطابق اسم الملف حرفياً (الملف عندي Index.css). أي فرق User.tsx vs user.tsx يكسر البناء على لينكس بس. الدرس: وحّد التسمية، وخليك واعي إن نجاح ويندوز مش ضمان إنتاج.

إيه فايدة /health؟

منصات النشر تعمل ping. لو السيرفر ميت تrestart. كمان أبسط إثبات إن الخدمة فوق من غير ما تعدي على مونجو (الـ health الحالي بيرجع ok بس — نسخة أقوى تفحص mongoose.connection.readyState).

13. التفكير في التوسع

1000 صيدلي بدل 10 — إيه اللي يحصل؟

البث العام io.emit هيزق كل الأحداث لكل العملاء. كل صيدلي هيستقبل شغل غيره ويعتمد على فلتر الفرونت. الحل: rooms موثّقة + شيل الـ broadcast. الطوابير find من غير index هتبطأ. الإشعارات الصوتية والريفetch الجماعي هيضغطوا الـ API.

Redis مش أول خطوة سحرية؛ أول خطوة توجيه صحيح + indexes. Redis يدخل لما تحتاج presence أو pub/sub عبر instances.

مليون روشتة — هل find() الحالي يكفي؟

لأ. هنحتاج indexes، pagination/cursor، وما نرجعش originalImage في قوائم الطوابير (projection). الصورة Base64 هتكبّر كل document وتقتل الـ memory. فصل الوسائط عن الميتاداتا.

Socket.IO على سيرفر واحد، وبعدين 5 instances؟

العميل ممكن يتوصل لـ instance A والصيدلي على B. io.to(room).emit محلي للبروسيس. الحل: Redis adapter لـ Socket.IO عشان الـ pub/sub بين النسخ. وكمان sticky sessions أو أن الـ adapter يكفي. Load balancer لازم يدعم WebSocket upgrade.

من غير كده: إشعارات ضايعة بشكل عشوائي. ده مثال كلاسيكي «الشغل على لابتوب يخفي مشكلة التوزيع».

Rate limiting, queues, caching, monitoring — إمتى؟
  • Rate limit: فورًا تقريبًا على /process و/auth لأن Gemini غالي وفي إساءة.
  • Queue: لما زمن Gemini يبقى أطول من تحمل HTTP أو يبطّئ باقي الـ API.
  • Cache: قائمة صيادلة/مناديب تتغير نادرًا.
  • Monitoring: logs منظمة، تنبيه على 5xx ونسبة فشل الدفع.

الجملة الذهبية: «المشكلة X تظهر عند حجم معيّن، وساعتها Redis/Queue مناسب لحل Y. على حجم الديمو الحالي الإضافة overengineering.»

  9. مفيش indexes على طوابير الروشتات.
  10. مطابقة أدوية regex هشّة.
  11. بيانات صحية (روشتات) من غير تشفير حقل أو سياسات احتفاظ — للديمو فقط، مش HIPAA.

الاعتراف المنظم أحسن من إن المحاور يكتشفها وإنت بتبرر.

15. أسئلة إضافية متوقعة — غطّي الزوايا الباقية

ليه مفيش GraphQL؟

REST كافٍ للموارد الواضحة. GraphQL تكلفة schema وN+1 وcaching. هفكر فيه لو الموبايل حابب يقلل over-fetch للقوائم.

ليه Vite مش CRA؟

سرعة ESM، بناء أحدث، ودعم Tailwind 4 plugin. CRA متوقف عملياً.

إيه فايدة seeder؟

بيانات أدوية وتداخلات للعرض من غير إدخال يدوي. يمسح Drug وInteraction ويعيد الإدراج. مش آمن على إنتاج فيه بيانات حقيقية — سكربت تطوير.

ترتيب الراوتات الديناميكية ليه في الآخر؟

/pharmacist-queue قبل /:id وإلا Express يفهم pharmacist-queue كأنه ObjectId. نفس الفكرة في userRoutes: /pharmacists قبل /:id.

ليه populate أحياناً ومرات لأ؟

الطابور الداخلي للصيدلي يكفي IDs. عرض التاريخ للمريض يحتاج اسم الصيدلي. populate تكلفة join منطقي؛ مش بحطه في كل query.

الأمان الطبي: ده تطبيق صحي؟

الديمو بيعالج بيانات حساسة (صورة روشتة، تليفون، عنوان). في الإنتاج الحقيقي: موافقة، تشفير at rest، Retention policy، عدم البث العام للسوكت، عدم رمي الصورة في كل إشعار. أنا بقدّمه كمشروع هندسي مش كمنتج طبي معتمد.

إزاي تختبر الـ checkout من غير ما تدمّر المخزن؟

Stripe test keys، كروت اختبار، وtransaction ترجع لو الكمية ناقصة. سيناريو السباق: طلبين متوازيين على آخر قطعة — واحد 409.

إيه أصعب باج هندسي اتعلم منه؟

جهّز قصتين من شغلك الفعلي:

  1. Listeners تتشال في الإنتاج: نقل الاشتراك لـ AuthInitializer.
  2. Case sensitivity / بيئة مختلفة: ويندوز vs لينكس، ORIGIN، FRONTEND_URL، PORT.

احكي: العرض → السبب الجذري → الإصلاح → الدرس المعماري. ده أقوى من أي تعريف محفوظ.

لو عندك أسبوع hardening قبل الإنتاج، الترتيب؟
  1. قفل drug routes + ملكية GET prescription و patient-decisions.
  2. JWT على السوكت، شيل io.emit العام، CORS مضبوط.
  3. Stripe webhook + idempotency.
  4. Error middleware + rate limit على AI واللوجين.
  5. صور على storage، projection للقوائم، indexes.
  6. تقصير عمر التوكن / httpOnly cookie لو الوقت يكفي.
جمل قصيرة تتقالي لو الوقت خلص
  • «الفرونت للتجربة، الباك للحقيقة.»
  • «الحالة آلة مش مجموعة أعلام.»
  • «السعر والمخزن والدفع مصدرهم السيرفر.»
  • «الـ real-time في الديمو موجّه بالنية، وفي الإنتاج موجّه بالتوكن.»
  • «كل أداة بتتحط لما الألم يظهر، مش لأنها trending.»
